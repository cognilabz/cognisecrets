# Security Model

## 1. Purpose

This document defines the security model for CogniSecrets.

CogniSecrets is a Secret composition controller. It is not a secret store, vault, encryption system, identity provider, or policy engine.

## 2. Security boundary

The primary security boundary is namespace-level authorization declared on each source Secret.

A target namespace may consume a source Secret only when the source Secret explicitly lists that target namespace in:

```text
cognisecrets.cognilabz.com/allowed-namespaces
```

Authorization applies to the whole source Secret.

## 3. Authorization rules

For every source Secret:

- missing annotation means denied;
- empty annotation means denied;
- target namespace must be explicitly listed;
- source namespace is not implicitly authorized;
- wildcard authorization is not supported;
- key selection does not reduce authorization scope;
- authorization is evaluated independently for every source.

If any source is not authorized, the complete target Secret MUST NOT exist unless it is a foreign Secret that CogniSecrets does not own.

## 4. Annotation parsing

The annotation value is parsed as a comma-separated list.

Rules:

- split on `,`;
- trim leading and trailing whitespace for each entry;
- ignore empty entries;
- ignore duplicate entries;
- compare namespace names exactly;
- reject `*` as unsupported.

Invalid namespace names SHOULD be ignored for authorization matching and SHOULD be reported through the failure message when they affect reconciliation.

## 5. Fail-closed behavior

CogniSecrets MUST prefer absence of a managed target Secret over stale or unauthorized data.

The managed target Secret MUST be deleted when:

- authorization is removed;
- a source Secret is deleted;
- a requested key is deleted;
- composition becomes ambiguous;
- a source is detected as CogniSecrets-managed;
- the generated Secret is rejected by Kubernetes.

Only managed target Secrets may be deleted.

## 6. Source ownership

CogniSecrets does not claim ownership over source Secrets.

Source Secret owners remain responsible for:

- deciding which namespaces may consume the Secret;
- adding or removing the authorization annotation;
- generating or rotating source values;
- encrypting source values at rest through existing Kubernetes or platform mechanisms.

## 7. Target ownership

CogniSecrets owns a target Secret only when the target Secret has a controller owner reference pointing to the current `SecretReference` UID.

The managed-by label is useful for discovery and chain prevention, but it is not a security proof.

Foreign target Secrets MUST NOT be adopted, overwritten, or deleted.

## 8. No key-level authorization

Key selection is not a security boundary.

If a namespace is authorized for a source Secret, it is authorized for the source Secret as a whole. The `keys` list only controls which values are copied into the target.

V1 MUST NOT support per-key allow or deny rules.

## 9. No transitive authorization

Secrets generated by CogniSecrets MUST NOT be used as sources.

This prevents hidden transitive access where a namespace receives values through an intermediate generated Secret that the original source owner did not explicitly authorize.

## 10. Threat model

CogniSecrets is designed to reduce these risks:

- accidental cross-namespace Secret duplication without source-owner approval;
- stale copied Secrets after source deletion or access revocation;
- accidental overwrite of application-owned Secrets;
- implicit overwrite precedence in multi-source composition;
- transitive Secret sharing through generated Secrets.

CogniSecrets does not solve:

- compromised Kubernetes API credentials;
- compromised controller service account;
- untrusted cluster administrators;
- weak etcd encryption configuration;
- insecure application handling of mounted Secrets;
- malicious mutation of source Secrets by actors that already have write access.

## 11. RBAC assumptions

Cluster operators MUST protect write access to source Secrets.

Any actor that can update a source Secret annotation can grant access to that Secret through CogniSecrets.

Any actor that can create `SecretReference` resources in a namespace can request authorized source Secrets for that namespace, but cannot bypass source-side authorization.

## 12. Auditing

The controller SHOULD emit events for access denial, target deletion, and successful synchronization.

Operators SHOULD be able to inspect:

- source Secret annotations;
- `SecretReference` specs;
- target Secret owner references;
- `Ready` conditions;
- controller logs.

## 13. Security non-goals

CogniSecrets does not provide:

- encryption;
- decryption;
- secret generation;
- secret rotation;
- external provider access;
- approval workflows;
- policy language;
- tenant isolation beyond Kubernetes namespace and RBAC primitives.
