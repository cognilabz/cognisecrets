# Design Principles

## 1. Purpose

This document defines the architectural principles that govern CogniSecrets. They are normative constraints for the API, controller implementation, documentation, and conformance tests.

When a proposed feature conflicts with one of these principles, the default decision is to reject the feature or redesign it so the principle remains intact.

## 2. Minimal Scope

CogniSecrets provides exactly one capability:

> Compose and synchronize one Kubernetes Secret from one or more existing Kubernetes Secrets.

CogniSecrets does not store, encrypt, decrypt, rotate, version, generate, or externally retrieve secret values.

New features must directly support Secret composition or synchronization. Convenience alone is not sufficient justification for expanding the scope.

## 3. Kubernetes-Native Concepts

CogniSecrets reuses Kubernetes concepts whenever they already exist.

Examples include:

- Kubernetes `Secret` objects remain the source and target data model.
- `metadata.name` and `metadata.namespace` identify resources.
- annotations express authorization on source Secrets.
- owner references express ownership of generated Secrets.
- status conditions express reconciliation state.
- Kubernetes validates Kubernetes Secret types.

CogniSecrets must not introduce an abstraction that duplicates an existing Kubernetes concept without a compelling technical reason.

## 4. One Resource, One Result

One `SecretReference` describes exactly one desired target `Secret`.

The target Secret:

- has the same name as the `SecretReference`;
- exists in the same namespace as the `SecretReference`;
- is owned by the `SecretReference`.

A `SecretReference` must never create multiple target Secrets. Multiple targets require multiple `SecretReference` resources.

## 5. Explicit Behavior

CogniSecrets avoids implicit shortcuts and hidden defaults that change resource identity or authorization.

In particular:

- every source explicitly specifies `namespace` and `name`;
- `sources` is always a list;
- there is no shorthand such as `namespace/name`;
- same-namespace access is not implicitly authorized;
- authorization is never inferred from naming conventions;
- source ordering never determines which duplicate value wins.

The only intentional defaults are simple value defaults with unambiguous meaning, such as:

- omitted `spec.type` means `Opaque`;
- omitted key `target` means the source key name is retained;
- omitted `keys` means all keys from that source are copied.

## 6. Explicit Authorization

A target namespace may read a source Secret only when the source Secret explicitly authorizes it through:

```yaml
metadata:
  annotations:
    cognisecrets.cognilabz.com/allowed-namespaces: "app-a,app-b"
```

Authorization applies to the complete source Secret, not to individual keys.

The following rules apply:

- a missing annotation denies access;
- only explicitly listed namespaces are allowed;
- the source namespace is not implicitly allowed;
- wildcard authorization is not supported;
- key selection is composition behavior, not an authorization boundary.

## 7. Fail Closed

If the desired target Secret cannot be computed correctly or is no longer authorized, CogniSecrets removes the managed target Secret.

Examples include:

- a source Secret no longer exists;
- a requested source key no longer exists;
- authorization is removed;
- two inputs produce the same target key;
- Kubernetes rejects the desired target Secret.

CogniSecrets must prefer no target Secret over a stale, ambiguous, invalid, or unauthorized target Secret.

Only a target Secret owned by the corresponding `SecretReference` may be deleted. Foreign Secrets must never be modified or deleted.

## 8. No Secret Chains

A Secret generated by CogniSecrets must not be used as a source Secret.

This rule prevents:

- recursive composition;
- dependency cycles;
- ambiguous propagation order;
- complex failure cascades;
- hidden transitive authorization.

Every source must be an original Kubernetes Secret that is not managed by CogniSecrets.

## 9. Deterministic Composition

The same cluster state must always produce the same desired target Secret.

Source ordering must not resolve conflicts. If two selected source values map to the same target key, reconciliation fails with `DuplicateTargetKey`.

A single source key may be copied more than once when each copy has a distinct target key.

The controller must fully recompute the desired target Secret during every reconcile. It must not depend on previous reconcile state or incremental key tracking.

## 10. Stateless Reconciliation

Each reconcile follows this model:

1. observe the current `SecretReference` and source Secrets;
2. validate authorization and composition semantics;
3. compute the complete desired target Secret;
4. compare the managed fields with the current target Secret;
5. create or update only when necessary;
6. update status.

The controller must not require a persistent internal cache or reconciliation history for correctness.

## 11. Event-Driven Synchronization

The controller watches both:

- `SecretReference` resources;
- Kubernetes `Secret` resources.

A field index maps source Secret identities to all referencing `SecretReference` resources. Source changes therefore enqueue only affected references.

Polling must not be the primary synchronization mechanism.

## 12. Structure in the CRD, Semantics in the Controller

The CRD validates structural constraints that can be expressed clearly and reliably, including:

- required fields;
- field types;
- minimum list sizes;
- basic Kubernetes name formats where appropriate.

The controller validates semantic constraints that depend on cluster state or relationships, including:

- source existence;
- authorization;
- source key existence;
- duplicate target keys;
- ownership conflicts;
- generated Secret validity as accepted by the Kubernetes API.

The CRD must not become unnecessarily complex in an attempt to encode controller semantics.

## 13. Kubernetes Owns Kubernetes Validation

CogniSecrets does not reproduce Kubernetes Secret-type validation.

`spec.type` is copied to the target Secret. When omitted, it defaults to `Opaque`.

The controller submits the desired Secret to the Kubernetes API. If the API rejects it, reconciliation fails and the managed target Secret is removed according to the fail-closed principle.

## 14. Narrow Field Ownership

CogniSecrets manages only the fields required for its contract:

- `data`;
- `type`;
- its own owner reference;
- `app.kubernetes.io/managed-by: cognisecrets`.

Foreign labels, annotations, finalizers, and unrelated owner references must be preserved.

Only managed fields are considered when deciding whether an update is necessary. Kubernetes-managed metadata such as `resourceVersion`, `uid`, and timestamps must not affect the comparison.

## 15. No Adoption or Overwrite

If a target Secret with the desired name already exists but is not owned by the current `SecretReference`, CogniSecrets must not adopt, overwrite, or delete it.

Reconciliation reports:

```text
Ready=False
Reason=TargetAlreadyExists
```

Ownership must be explicit and authoritative.

## 16. Idempotence and Minimal Writes

Repeated reconciliation against unchanged cluster state must not change the target Secret.

Before writing, the controller compares only its managed fields. It creates or updates the target Secret only when those fields differ from the desired state.

This avoids unnecessary API writes, resource-version changes, and downstream watch events.

## 17. Small Status Model

`SecretReference` exposes one `Ready` condition.

Successful synchronization reports:

```text
Ready=True
Reason=Synced
```

Failures report `Ready=False` with one precise reason. The status model must remain small and operationally useful rather than becoming a second state machine.

## 18. Specification Before Implementation

The project is developed in this order:

1. product and architecture documentation;
2. API and controller specifications;
3. lifecycle, security, and error specifications;
4. conformance tests;
5. implementation.

Implementation choices must conform to the specification. Tests are the executable proof of that conformance.

## 19. Decision Rule for Future Features

A proposed feature should be accepted only when all of the following are true:

1. it directly supports Secret composition or synchronization;
2. Kubernetes does not already provide the capability;
3. it does not weaken explicit authorization or fail-closed behavior;
4. it preserves deterministic and stateless reconciliation;
5. it does not introduce a second abstraction for an existing Kubernetes concept;
6. its behavior can be specified and tested unambiguously.

If these conditions are not met, the feature is outside the intended scope of CogniSecrets.
